We have our @Component decorator here which is metadata for the ts class to tell angular how to treat is as a component (you can see we have the selector 'app-root' here which is loaded in the level above: index.html). So whenever we click around on the app we will be updating our route, this will get the html code for that page, then display it. We also have our left side nav with the theme footer in this html page, they are shown constantly. So when we update the router outlet, it is just the content section that is being updated. Side note: We also have to import routerLink and routerLinkActive in the app.ts file so that we can use them in the app.html file.
- Our globall css such as theme stuff is in [styles.css](../frontend/src/styles.css) but we do have specific component styles, shown by the templateUrl and styleUrl within the @Component decorator defined in app.ts, so for the class/component App we have those specific files (**app.html** and **app.css**)
- Okay now outside of the angular decorator stuff we have the actual ts code for the class. We 'inject(ThemeService)' here. That is referring to this file of course: [theme.service.ts](../frontend/src/app/services/theme.service.ts). inject() fetches one shared instance of a service, and different components can each get a refernce to that same instance. The theme service file gets a little bit complicated, but the most important thing is the '@Injectable({ providedIn: 'root'})', this is the part that is telling Angular to make exactly one of these for the whope app, and hand out exactly one of these for the whole app. For example the TaskService is injected in both the Dashboard and the ToDoList components, and they refer to the exact same thing. So this is the more modern approach I'd say, rather than doing 'const themeService = new ThemeService();' and new giving us a fresh object each time, we use a singleton approach with inject.

**signals & theme**
'private themeSignal = signal<ThemeName>(this.loadTheme());' &   'readonly theme = this.themeSignal.asReadonly();' is the signal defined in our theme.service.ts file. A signal is a box holding a value that notifies interested parties when it changes. 
- You read it by calling it — theme() — and that's why app.html:30 has t === theme(), not t === theme. When something calls themeSignal.set(...), Angular knows exactly which templates read that signal and updates only those.
- The write side is private (only the service should write to the signal), the read side is public (the components get a readonly view of the signal). Components get theme (read-only) and must go through setTheme(...) to change it. That means the one place something can go wrong is one method in one file — when something breaks, you know where to look.
- Side note: Our app holds no state of its own — theme lives in the singleton ThemeService as a signal, and the theme picker is just "read the signal to highlight the dot, call the service to change it."

**storage/backend changes - Moving from localStorage to REST API**
- So we have had localStorage so far, and we are planning to move away from it towards using backend API. Firstly I made a change where we had duplicated code in each of the 3 services that loaded the data from the localStorage, I've moved this to one place now at persisted-signal.ts. So the effect() in the constructor and the load stuff can be deleted.
- Where we are at right now:
Right now JakeOS is one program: the Angular app, running entirely inside your browser. When it needs to remember something overnight, it uses localStorage — which is just a little per-website key-value store the browser keeps on your hard drive. The whole lifecycle of your data happens on one machine, inside one browser:
Angular app ──▶ persistedSignal() ──▶ localStorage (a file your browser manages)
That works, but the limits are baked in: the data exists only in that browser on that machine. Open JakeOS on your phone — empty. Clear site data — gone. There's no "your data" anywhere except that one browser profile.
- A backend is a second, separate program that owns the data. It runs on its own — during development it'll just be another process on your laptop, started in another terminal — and it does two jobs: store data durably (in a real database) and answer questions about it. Your Angular app then stops being the keeper of the data and becomes a client: something that asks for data.
- Today, adding a task: addTask() updates the signal → the seam's effect() fires → localStorage.setItem. 
After: addTask() updates the signal → the seam sends POST http://localhost:8000/tasks with the task as JSON → FastAPI receives it, writes a row into the SQLite file, responds → done. Same first half, different second half — which is exactly what "seam" meant.
